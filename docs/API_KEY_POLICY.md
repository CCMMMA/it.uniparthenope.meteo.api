# API-Key and Endpoint Access Policy

## 1. Purpose

API keys identify non-human client applications, support attributable usage
measurement, and provide a basis for scopes and quotas. They are not user login
credentials and do not replace operator authentication for administrative
actions.

This policy separates domain capability from enforcement. The request, issue,
validate, rotate, and revoke services are implemented first. Existing endpoints
remain behaviorally unchanged until authentication middleware and public
management endpoints are released with dedicated compatibility tests.

## 2. Endpoint classification

| Class | Examples | Intended policy |
| --- | --- | --- |
| Public infrastructure | `/`, `/swagger.json`, `/api/v1`, `/version` | No API key; supports discovery and diagnostics. |
| Public legal | `/legal/disclaimer`, `/legal/privacy` | No API key; legal terms must remain inspectable before credential use. |
| Public v1 metadata | `/api/v1/products` and product metadata/availability | Public during the adoption phase; eligible for an anonymous low quota later. |
| Transitional legacy | Existing unversioned read endpoints and retained `/v2` endpoints | No enforcement change until a versioned replacement and deprecation notice exist. |
| Consumer protected | Future v1 forecast, time-series, image, GRIB, tile, and bulk place resources | Valid API key plus the resource scope. |
| Operator protected | Cache invalidation/rebuild and API-key issuance, rotation, and revocation interfaces | Separate operator authentication; a consumer key alone is insufficient. |

Submitting an API-key request may become a public operation, but it must be
protected by input validation, abuse controls, and out-of-band ownership
verification. Issuance is never public.

## 3. Scope catalogue

| Scope | Authorizes |
| --- | --- |
| `products:read` | Product catalogue, availability, maps, themes, fields, and outputs. |
| `places:read` | Place search and place metadata. |
| `forecast:read` | Structured forecast resources. |
| `timeseries:read` | Structured and downloadable time-series resources. |
| `imagery:read` | Plot, legend, Skew-T, tile, and other rendered resources. |
| `operations:cache` | Cache invalidation and rebuild, only when operator authentication also succeeds. |
| `keys:admin` | Key administration, only when operator authentication also succeeds. |

Services enforce least privilege: requested scopes are normalized and checked
against the configured allow-list, while validation requires every scope named
by the endpoint.

## 4. Credential format and storage

Issued credentials have two components:

```text
meteo_<environment>_<public-id>.<secret>
```

The prefix is a non-secret lookup identifier and may appear in audit logs. The
secret contains at least 256 bits generated by Python's cryptographically secure
`secrets` module. The plaintext credential is returned only by issuance or
rotation and cannot be recovered later.

Persistence stores the public prefix, a random salt and memory-hard scrypt
verifier, owner and scope metadata, lifecycle status, and audit events. It must
never store or log the plaintext credential. Secret comparison uses constant-
time comparison. Keys in URLs and query parameters are forbidden; future
middleware will accept an explicit request header and redact it from logs.

## 5. Lifecycle

1. **Request:** a consumer supplies identity, organization, purpose, and scopes.
2. **Review and issuance:** an authenticated operator selects approved scopes
   and lifetime. The service records the reviewer and returns the secret once.
3. **Validation:** the prefix locates the record; status, expiry, scrypt
   verifier, and required scopes are checked.
4. **Rotation:** a replacement is created with a new prefix, salt, and secret;
   the previous credential becomes invalid immediately and remains auditable.
5. **Revocation:** the record becomes inactive without being deleted.
6. **Expiration:** validation marks an elapsed active credential as expired.

Management operations are transactional. Rotation either persists the new key
and invalidates the old key together, or neither transition is committed.

## 6. HTTP enforcement contract (future middleware)

When enforcement is enabled for a resource, missing or invalid credentials
return `401`, insufficient scope returns `403`, and exhausted quotas return
`429` with retry metadata. Errors must use a stable v1 envelope without
revealing whether a prefix exists.

Legacy routes must not begin requiring keys merely because their v1 replacement
is published. Enforcement and deprecation require a separately announced,
tested migration step.

### Current observation-only phase

Legacy routes currently accept an optional `X-API-Key` header. When present,
middleware validates identity and the future route scope, records a structured
diagnostic log, and returns one of these non-enforcing response headers:

```http
API-Key-Observation: valid
API-Key-Observation: invalid
API-Key-Observation: unavailable
```

All three outcomes continue to the legacy handler unchanged. Missing keys do not
produce the header. `/api/v1` is excluded from this transitional middleware;
authentication for governed resources will be introduced by an explicit v1
contract change. Logs contain only the non-secret key prefix.

## 7. Audit and privacy

Lifecycle events record request/key identifiers, action, actor, timestamp, and
minimal structured context. Secrets and secret hashes are excluded from domain
serializers and event data. Request-level usage telemetry is a separate concern:
it may reference the public key identifier but must define retention, IP-address
handling, aggregation, and access controls before collection begins.
